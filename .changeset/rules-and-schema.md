Rules check `@request.auth.<field>` when they are saved: a name no auth collection has is an error instead of an empty value, so renaming or deleting an auth field a rule reads is refused like other changes that break a rule. Hidden fields of the signed-in record can be read, and a field with several values compares like one of the record's own, so `@request.auth.roles ?= "admin"` works instead of failing every signed-in request. A modifier a `@request` value does not support, such as `@request.query.q:lower`, is an error instead of being ignored. Deleting a collection that another rule reads with `@collection` is refused instead of blocking every later schema change. A `~` pattern ending in a lone backslash and an index over values too large to index are 400 errors instead of 500s. A collection cannot be named another collection's id, or take another's name as its id, and `true`, `false` and `null` are reserved field names. Upgrading a database whose auth collections have their own `phone`, `phoneVerified` or `emailVerified` field renames that field to `user_<name>`, with the rules that use it, instead of failing at every startup.
