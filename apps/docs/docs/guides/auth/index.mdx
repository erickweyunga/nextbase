# Authentication

Users live in **auth collections**. An auth collection has the system fields
`email`, `emailVisibility`, `emailVerified`, `phone`, `phoneVerified` and `password`; you add your own fields.
Each signed-in user gets a session in the database, which you can list and
revoke.

## Create a users collection

As a superuser, for example from a one-time script:

```ts title="scripts/setup-auth.ts"
import { NextBase } from "@nextbasejs/core";

const superuser = new NextBase().client({ superuser: true });

await superuser.collections.create({
  name: "users",
  type: "auth",
  createRule: "", // anyone can sign up
  viewRule: "id = @request.auth.id", // users see only themselves
  updateRule: "id = @request.auth.id",
  deleteRule: "id = @request.auth.id",
  fields: [{ name: "name", type: "text", required: true }],
});
```

A rule of `""` allows anyone, `null` allows only superusers, and anything else
is a filter the request must match.

## Ways to sign in

- [Email & Password](/docs/guides/auth/email-password): sign up, sign in and
  sign out, with optional email verification.
- [OAuth2](/docs/guides/auth/oauth2): sign in with Google, GitHub or any
  OpenID Connect provider.
- [Phone](/docs/guides/auth/phone): sign in with a code texted to a phone, or
  with a phone and password.
- [Email code](/docs/guides/auth/email-code): sign in with a code emailed to
  the account, with no password.
- [Passkeys](/docs/guides/auth/passkeys): sign in with the device's
  fingerprint, face or PIN, with no password.
- [Multi-factor](/docs/guides/auth/mfa): a second step after any of these,
  with an authenticator app, a recovery code, or a code sent by email or text.

## Decide who may sign in

`validateSignIn` runs at every sign-up, OAuth2 link and sign-in, by every
method, and refuses by answering an error code:

```ts title="lib/nextbase.ts"
export const nextbase = new NextBase({
  validateSignIn({ action, method, collection, record, oauth2 }) {
    // Your provider's email, as it is now, or the account's.
    const email = String(oauth2?.profile.email ?? record.email ?? "");
    if (collection === "users" && !email.endsWith("@example.com")) {
      return { error: "email_not_allowed", message: "Use your example.com email." };
    }
  },
});
```

| Field | Description |
| ----- | ----------- |
| `action` | `sign-up`, `link` (an OAuth2 provider linked to an existing account by its email) or `sign-in`. Each starts a session, so a check on existing accounts handles `link` and `sign-in`. |
| `method` | `password`, `oauth2`, `phoneCode`, `emailCode` or `passkey`. |
| `collection` | The auth collection's name. |
| `record` | The account as stored; for a sign-up, the values it is to be created with. Never the password or `tokenKey`. |
| `oauth2` | For OAuth2: `provider`, and `profile`, what the provider says about the account at this sign-in. |

A refusal answers `403` with the message, and the code in
`data.account.code`; an OAuth2 sign-in in the browser comes back with
`?error=` and the code. Accounts callers create through the records API, or
in a batch, are checked as sign-ups too; a superuser's are not. A sign-up is
refused before anything is written, and
the same whether or not the email is registered, so it reveals nothing. The
second step of a [multi-factor](/docs/guides/auth/mfa) sign-in and session
refreshes are not checked again. For rules that only read the stored account,
the collection's `authRule` does the same.

## Account emails

With [email sending](/docs/guides/auth/email) set up, users can
[verify their email](/docs/guides/auth/verification),
[reset a forgotten password](/docs/guides/auth/password-reset) and
[change their email](/docs/guides/auth/email-change).

## Sessions

Every sign-in creates a session that you keep in an HttpOnly cookie or as a
Bearer token. See [Sessions and cookies](/docs/guides/auth/sessions).

## Protections

- Passwords are hashed with scrypt.
- Failed sign-ins are limited per account, and repeated emails per address.
- A password reset or email change signs out every session.
- Sign-in, verification and password reset requests never reveal whether an
  email is registered. Sign-up hides it too once
  [verification is required](/docs/guides/auth/verification#options).
- With [multi-factor sign-in](/docs/guides/auth/mfa), a stolen password alone
  does not sign in.
