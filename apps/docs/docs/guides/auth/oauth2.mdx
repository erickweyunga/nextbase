# OAuth2

Users can sign in with an account they already have at Google, GitHub, or any
OpenID Connect provider, such as Microsoft, Auth0, Okta or Keycloak. The
first sign-in creates their account; later ones sign in to it.

## Set up a provider

1. Register an OAuth app at the provider. As its **redirect URI** (also called
   callback URL), enter your app's URL followed by the base path, `/callback/`
   and the provider's name, as you name it in the `oauth2` option:

   ```text
   https://example.com/api/nextbase/callback/google
   ```

2. Pass the app's URL and the provider's credentials to NextBase:

   ```ts title="lib/nextbase.ts"
   import { NextBase } from "@nextbasejs/core";

   export const nextbase = new NextBase({
     appUrl: "https://example.com",
     oauth2: {
       google: {
         clientId: process.env.GOOGLE_CLIENT_ID!,
         clientSecret: process.env.GOOGLE_CLIENT_SECRET!,
       },
       github: {
         clientId: process.env.GITHUB_CLIENT_ID!,
         clientSecret: process.env.GITHUB_CLIENT_SECRET!,
       },
       // Any OpenID Connect provider, by its issuer:
       microsoft: {
         issuer: "https://login.microsoftonline.com/<tenant>/v2.0",
         clientId: process.env.MICROSOFT_CLIENT_ID!,
         clientSecret: process.env.MICROSOFT_CLIENT_SECRET!,
         displayName: "Microsoft",
       },
     },
   });
   ```

| Option | Description |
| ------ | ----------- |
| `clientId` | Required. From the provider's OAuth app. |
| `clientSecret` | Required. Keep it in an environment variable, never in code. |
| `issuer` | Required except for `google` and `github`. The provider's OpenID Connect issuer; NextBase discovers its endpoints from it. |
| `displayName` | Optional. The name to show on sign-in buttons. |

`appUrl` must be the address users open your app at, and serve NextBase: the
sign-in starts and ends there. Redirects are always built from it, never from
the request.

## Sign in

Send the browser to the provider. It comes back to `redirect`, a path on your
app, signed in with a session cookie, or to `errorRedirect` when the sign-in
fails:

```tsx
"use client";

import { useNextBase } from "@nextbasejs/react";

export function SignInWithGoogle() {
  const nb = useNextBase();
  return (
    <button
      type="button"
      onClick={() =>
        nb.collection("users").signInWithOAuth2("google", {
          redirect: "/dashboard",
          errorRedirect: "/sign-in",
        })
      }
    >
      Continue with Google
    </button>
  );
}
```

`oauth2Url(provider, options)` returns the same URL for a plain link. To build
buttons from the providers you set up, read them from `listAuthMethods()`:

```ts
const { oauth2 } = await nb.collection("users").listAuthMethods();
// oauth2.providers: [{ name: "google", displayName: "Google" }, ...]
```

## When a sign-in fails

The browser comes back to `errorRedirect`, or `redirect` without it, with
`?error=` naming what went wrong. Point `errorRedirect` at a page that does not
need a session, such as your sign-in page, so the error is not lost on the way:

| Error | Meaning |
| ----- | ------- |
| `oauth2_denied` | The user cancelled at the provider. |
| `oauth2_failed` | The sign-in took too long, started in another browser, or the provider failed. The server log has the details. |
| `account_exists` | An account with this email exists but cannot be linked automatically (see below). Sign in to it, then link the provider. |
| `email_required` | The provider did not share an email address, which a new account needs. |
| `email_not_verified` | The provider did not verify the email it shared, or the account linking a provider has not verified its email. |
| `sign_up_disabled` | The collection's `createRule` does not allow this sign-up. |
| `sign_up_failed` | The new account is invalid, for example because the collection has a required field the provider cannot fill. |
| `sign_in_forbidden` | The account exists but the collection's `authRule` does not let it sign in yet. |
| `already_linked` | The provider account belongs to another user, or this user already linked one from this provider. |

## New accounts

A first sign-in creates an account under the collection's `createRule`, as a
sign-up does. Its email comes from the provider and counts as verified. A
provider that did not verify the email creates no account; the sign-in fails
with `email_not_verified`. The account gets a random password that nobody
knows; to sign in with a password too, the user sets one through
[password reset](/docs/guides/auth/password-reset).

## Existing accounts with the same email

A user is found by the provider's permanent account id, never by email. When
a new provider account has the email of an existing account, NextBase links
them automatically only when **both** the provider and NextBase verified that
email, and then emails the account to say a new way to sign in was added.
Otherwise the sign-in fails with `account_exists`: the user signs in the way
they usually do and links the provider from their account.

This keeps someone who controls a provider account claiming your email from
signing in to your account.

Two cases never link automatically, and answer `account_exists` instead:

- an account that takes a [second sign-in step](/docs/guides/auth/mfa):
  whoever holds its inbox could otherwise add a provider and count it as a
  second step beside an email code;
- every account of a collection with `implicitLinking: false`, for apps that
  want users to link providers only from a settings page:

```ts
await superuser.collections.update("users", { implicitLinking: false });
```

New users can still sign up through a provider either way.

## Link and unlink providers

A signed-in user, with a cookie session, can link a provider to their
account. The sign-in session stays as it is:

```ts
await nb.collection("users").linkOAuth2("github", {
  password, // the current one
  redirect: "/settings",
});
```

The account's email must be [verified](/docs/guides/auth/verification) first,
or the link fails with `email_not_verified`. Otherwise someone could sign up
with your email before you do, link their own provider, and keep signing in
with it after you reset the password.

List and unlink a user's providers. Linking or unlinking emails the account,
so its owner hears of a change they did not make:

```ts
const users = nb.collection("users");
const linked = await users.listLinkedAccounts(user.id);
// [{ id: "...", provider: "github", created: "2026-10-19T12:00:00.000Z" }]
await users.unlinkAccount(user.id, "github", { password });
```

Linking and unlinking need the current password, and with an
[authenticator app](/docs/guides/auth/mfa) a code from it as `mfaCode`, so
someone who took over a session cannot add or remove a way in. A superuser
unlinking another account's provider needs neither. The link starts with a
`POST`, which answers the provider's URL; `linkOAuth2` opens it, and
`oauth2LinkUrl` returns it.

## Protections

- Only the browser that started a sign-in can finish it: a one-time `state`
  is checked against an HttpOnly cookie set when the sign-in started.
- The code the provider returns is useless to anyone who intercepts it: it
  can only be exchanged together with a secret (PKCE) that never leaves the
  server.
- An ID token from another sign-in is refused: its `nonce` must match.
- Each provider has its own callback, and a sign-in must return from the
  provider it went to.
- `redirect` must be a path on your app, so a sign-in can never send users to
  another site.
- Superusers always sign in with their password.
