# Sessions and cookies

Every sign-in creates a session in the database. The client proves who it is
on later requests with the session's token, which it keeps in one of two ways:

- **In a cookie** the browser sends by itself. Scripts cannot read it, and
  server components can see who is signed in.
- **As a Bearer token**: the client stores the token and sends it in the
  `Authorization: Bearer <token>` header of each request.

**In a Next.js app, use the cookie.** It is the only way for server components
and server actions to know the user, and it keeps the token out of reach of
injected scripts. Use Bearer tokens for mobile apps, scripts and other servers,
which have no browser to keep a cookie.

| | Bearer token | Session cookie |
| - | - | - |
| Sign in | `signInWithPassword(email, password)` | `signInWithPassword(email, password, { cookie: true })` |
| Readable by scripts | Yes | No |
| Sent on page loads | No | Yes |
| Server components | No | Yes |
| Use for | Mobile apps, scripts, other servers | Next.js apps |

## Sign in with a cookie

```ts
await nb.collection("users").signInWithPassword(email, password, { cookie: true });
```

The response sets the session as an `HttpOnly`, `SameSite=Lax` cookie and
returns no token. Over HTTPS and in production, the cookie is
`__Host-nextbase_session` and `Secure`, so no other subdomain can set or
overwrite it; in development over plain HTTP it is `nextbase_session`. Restore the signed-in user after
a reload with `nb.getSession()`.

## Read the user in a server component

With the `nb()` helper from [the Next.js guide](/docs/integrations/nextjs#add-a-server-helper):

```tsx title="app/page.tsx"
import { nb } from "@/lib/nextbase";

export default async function Page() {
  const client = await nb();
  const session = await client.getSession();
  return <p>{session ? `Hi ${session.record.name}` : "Not signed in"}</p>;
}
```

The client calls NextBase directly, without an HTTP request, and applies the
same validation and rules as the REST API. Create one per request.

## Sign in and out from a server action

```ts title="app/actions.ts"
"use server";
import { nb } from "@/lib/nextbase";

export async function signIn(form: FormData) {
  const client = await nb();
  await client
    .collection("users")
    .signInWithPassword(String(form.get("email")), String(form.get("password")), {
      cookie: true,
    });
}

export async function signOut() {
  await (await nb()).signOut();
}
```

## Lifetime and revocation

- Sessions last 7 days (superusers: 1 day) and are extended while in use, at
  most once a day: by requests to the API, and by server actions and route
  handlers. Server components cannot set cookies, so they never extend a
  session.
- However active, a session ends 30 days after sign-in.
- `nb.listSessions()` lists the user's devices, `nb.revokeSession(id)` signs
  one out, and `nb.revokeOtherSessions()` signs out every device but this one.
- Deleting an account ends all of its sessions.
- Changing a password ends every other session, as does turning on an
  [authenticator app](/docs/guides/auth/mfa). Rotating the collection's auth
  secret ends all of its sessions.
- A superuser can [impersonate](/docs/guides/auth/impersonation) a user, for at
  most an hour. That session shows in the user's `listSessions()` with
  `impersonatedBy`, the superuser's id, and they can revoke it like any other.

## How it signed in

Each session lists the ways it proved who signed in, as `methods`: such as
`["password"]`, or `["password", "totp"]` after a
[second step](/docs/guides/auth/mfa). They come back in sign-in responses, in
`nb.getSession()` and in `nb.listSessions()`. Rules read
`@request.auth.mfa`, which is `true` with two different methods. Sessions
created before methods were recorded have none.

## Cross-site protection

A write that authenticates with the cookie must carry an `Origin` header
naming your site, or it gets a 403. Another site cannot sign a browser in with
an account of its choosing either.
