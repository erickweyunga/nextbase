# Files

A `file` field stores uploaded files on a record: avatars, attachments,
documents. The field holds the files' names; the files themselves live in
storage, on local disk or in an S3-compatible bucket.

## Add a file field

```ts
await superuser.collections.update("users", {
  fields: [
    {
      name: "avatar",
      type: "file",
      maxSize: 2 * 1024 * 1024, // bytes; default 5 MiB
      mimeTypes: ["image/png", "image/jpeg", "image/webp"],
      thumbs: ["300x200", "64x64"],
    },
    { name: "documents", type: "file", maxSelect: 10, protected: true },
  ],
});
```

| Option | Description |
| ------ | ----------- |
| `maxSelect` | How many files the field holds. Above 1, the value is an array. Default 1. |
| `maxSize` | The largest file allowed, in bytes. Default 5 MiB. |
| `mimeTypes` | The types allowed, such as `image/png`. Empty allows any. |
| `protected` | Serve the files only to callers the collection's view rule allows. Default `false`. |
| `thumbs` | The [thumbnail](#thumbnails) sizes images may be requested in, such as `300x200`. Up to 20; `100x100` is always allowed. Default `[]`. |

## Upload files

Pass `File` or `Blob` objects in the record's values. The SDK sends them as
form data:

```ts
const input = document.querySelector<HTMLInputElement>("#avatar");
await nb.collection("users").update(user.id, {
  name: "Ann",
  avatar: input.files[0],
});
```

The same works in `create`, `signUp`, and server code calling NextBase
in-process.

Each file is stored under a name NextBase generates from the original one,
such as `my_photo_k3j2h1g9f8.jpg` for `My Photo.JPG`, and the record holds
that name:

```json
{ "id": "u7v8w9x0y1z2a3b", "name": "Ann", "avatar": "my_photo_k3j2h1g9f8.jpg" }
```

### Add, keep and remove files

For a field with several files:

```ts
const docs = nb.collection("users");

// Add files after the ones the record has, or with "+documents", before them.
await docs.update(user.id, { "documents+": [fileA, fileB] });

// Remove files by name.
await docs.update(user.id, { "documents-": ["report_k3j2h1g9f8.pdf"] });

// Replace the list: names to keep, in order, and new files.
await docs.update(user.id, {
  documents: ["report_k3j2h1g9f8.pdf", newFile],
});

// Remove all files.
await docs.update(user.id, { documents: [] });
```

Removed files are deleted from storage, with their thumbnails. So are a record's files when the
record is deleted, a field's files when the field is removed, and a
collection's files when the collection is deleted. If a write fails, any file
it stored is deleted again, and the files it would have removed are kept.

## Show files

`nb.files.getUrl(record, name)` returns the file's URL, for links and `<img>`
tags:

```tsx
<img src={nb.files.getUrl(user, user.avatar)} alt="" />

<a href={nb.files.getUrl(user, doc, { download: true })}>Download</a>
```

Images, PDFs, video, audio and plain text are shown in the browser. Other
types, including HTML and SVG, which could run scripts, are always
downloaded. Downloads support byte ranges, so video players can seek.

### Thumbnails

Pass `thumb` to get a JPEG, PNG, GIF or WebP image in one of the field's
`thumbs` sizes, or in `100x100`:

```tsx
<img src={nb.files.getUrl(user, user.avatar, { thumb: "64x64" })} alt="" />
```

| Size | Thumbnail |
| ---- | --------- |
| `WxH` | Cropped to fill `W` by `H`, from the centre. |
| `WxHt` | Cropped to fill, from the top. |
| `WxHb` | Cropped to fill, from the bottom. |
| `WxHf` | Fit inside `W` by `H`, keeping the whole image. |
| `0xH` | `H` high, keeping the aspect ratio. |
| `Wx0` | `W` wide, keeping the aspect ratio. |

Sizes are written without leading zeros, with sides up to 2500 pixels, and
`t`, `b` and `f` only when neither side is 0. A thumbnail is never larger
than its image, so it can be smaller than the size asked for: a 200x50 image
at `100x100` gives 100x50. It keeps its format, and is turned the way the photo's EXIF orientation says; EXIF
and other metadata are left out. An animated GIF gives a still of its first
frame.

Each thumbnail is made the first time it is requested, stored beside its
file, and served from storage after that, with the same rules, headers and,
with a bucket, signed redirects as the file itself. Thumbnails are deleted
with their file. Thumbnails of a size removed from `thumbs` stay in storage
until then.

Otherwise, the request redirects (302, not cached) to the original file's
own URL, without `thumb`: for a size the field does not list, other types of
file, including SVG, files over 50 MB, images that cannot be read, have more
than 50 megapixels, a side over 16384 pixels or one side more than 50 times
the other, and while the server is too busy making other thumbnails. Images
whose header shows they can never be thumbed are remembered beside the file,
so they are tried once. When resizing an image fails, that size is tried
again after 5 minutes. Both are logged as warnings with `data.type`
`"thumbs"`.

Thumbnails are made with [sharp](https://sharp.pixelplumbing.com), which you
install in your app:

```sh
npm install sharp
```

Without it, requests redirect to the originals, and a warning is logged once
per instance. Next.js
leaves sharp out of its server bundles by default, since it has native code,
so it needs no configuration there. sharp installs a native build for the
platform it is installed on: install your dependencies where the app is
built for its servers, as Vercel does.

### Protected files

Files of a `protected` field are served only to callers the collection's
**view rule** allows. A session cookie works as is. Where no cookie is sent,
such as from a mobile app, get a short-lived file token:

```ts
const token = await nb.files.getToken(); // valid for 2 minutes
const url = nb.files.getUrl(user, doc, { token });
```

Files of fields that are not protected are public: anyone with the URL can
download them. URLs contain the record id and a random part, so they cannot
be guessed, but use `protected` for anything private.

## How files are checked

- The type is read from the file's first bytes, not from the label the
  browser sends, which anyone can set. A text file labeled `image/png` is
  refused by a field that allows only images, and an SVG labeled as plain
  text is still an SVG. Images, documents, archives, media, SVG and other XML
  formats are recognized this way. Formats without recognizable bytes, such
  as plain text, CSV, JSON and HTML, keep their label; they are served with
  `nosniff` and, except plain text, as downloads, so a wrong label cannot
  make them run.
- Sizes and counts are checked against `maxSize` and `maxSelect`.
- Stored names are generated: original names, which could contain paths or
  misleading extensions, are never used as they are.
- Files are served with `X-Content-Type-Options: nosniff` and a content
  security policy that runs nothing, so a file can never act as a page of
  your app.

Who may add or remove files is decided by the collection's create and update
rules, as for any other field. `@request.body.avatar` holds the file names
the write would leave on the record.

## Store files in a bucket

Without configuration, files are stored on local disk in `.nextbase/storage`,
which suits development and servers with a persistent disk; add `.nextbase/`
to your `.gitignore`. Serverless hosts such as Vercel keep no files between
requests: configure a bucket there.

```ts title="lib/nextbase.ts"
export const nextbase = new NextBase({
  storage: {
    s3: {
      bucket: process.env.S3_BUCKET!,
      region: process.env.S3_REGION, // AWS: the bucket's region. Default "auto".
      endpoint: process.env.S3_ENDPOINT, // other providers, such as Cloudflare R2
      accessKeyId: process.env.S3_ACCESS_KEY_ID,
      secretAccessKey: process.env.S3_SECRET_ACCESS_KEY,
    },
  },
});
```

| Option | Description |
| ------ | ----------- |
| `bucket` | Required. |
| `region` | The bucket's region on AWS. Defaults to `auto`, which Cloudflare R2 expects. |
| `endpoint` | The service URL for providers other than AWS, such as `https://<account>.r2.cloudflarestorage.com`. |
| `accessKeyId`, `secretAccessKey` | Optional. Without them, the AWS SDK's usual credential sources apply. |
| `forcePathStyle` | Address buckets as `endpoint/bucket`, as MinIO needs. |

With a bucket, downloads redirect to a signed URL that works for 5 minutes,
so large files never pass through your server.

### Large files

Vercel limits request bodies to 4.5 MB. With a bucket, when a write's files
add up to more than 4 MB, the SDK uploads the largest straight to the bucket
instead, until the rest fit, and the record takes them over once they arrive,
after the same type and size checks. Batches are sent as JSON, so the SDK
uploads all of their files this way, and batches with files need a bucket. This needs
nothing in your code, but the bucket must accept uploads from your site.
Add a CORS rule to the bucket, for example on AWS S3:

```json
[
  {
    "AllowedOrigins": ["https://example.com"],
    "AllowedMethods": ["PUT"],
    "AllowedHeaders": ["content-type"],
    "MaxAgeSeconds": 3600
  }
]
```

Uploads that no record takes within 15 minutes are deleted the next time an
upload starts. To clean up after a server that stops for good, you can also
add a lifecycle rule that expires objects under `_uploads/` after a day.

Without a bucket, large files are sent with the record, up to 32 MiB per
request.

## Limits

- The batch API takes JSON only. With a bucket, files can still be added in
  a batch: start each upload with the [upload URL endpoint](/docs/api/files#start-a-direct-upload)
  and pass the upload tokens as the field's values.
