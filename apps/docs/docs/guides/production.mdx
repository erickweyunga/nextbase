# Going to production

:::warning

NextBase is in early development and not recommended for production yet.
Until version 1.0, releases may change the API and the database layout. This
page describes how it is designed to run.

:::

## Runtime

NextBase runs on the Node.js runtime, the Next.js default for route handlers.
The Edge runtime is not supported: it cannot open TCP connections to Postgres.

`new NextBase()` never connects in its constructor, so `next build` works
without a database. The first request connects, creates or upgrades
NextBase's tables, and loads the schema.

## Database

Any Postgres 16 or later works, including Neon, Supabase, RDS and a local
server.

```sh
DATABASE_URL=postgres://user:password@host:5432/app
```

Or pass a pool, for example Neon's serverless driver:

```ts
import { Pool } from "@neondatabase/serverless";
import { NextBase } from "@nextbasejs/core";

export const nextbase = new NextBase({
  database: new Pool({ connectionString: process.env.DATABASE_URL }),
});
```

- **Connection poolers:** NextBase works behind PgBouncer (including its
  transaction mode) and the poolers of Neon, Supabase and RDS Proxy. Use the
  pooled connection string on serverless platforms. [Realtime](#realtime)
  also needs a direct connection to listen on.
- **The pool:** with a connection string, NextBase keeps one `pg` pool per
  string, with up to 10 connections. Idle connections close after 5 seconds,
  so a suspended serverless instance lets them go, and on Vercel they are
  released before the function suspends. A request waits at most 10 seconds
  for a connection. Pass your own pool to change these; NextBase never ends a
  pool you pass in.
- **TLS:** set it in the connection string. `?sslmode=require` encrypts the
  connection and, as `pg` reads it, also checks the server's certificate,
  like `verify-full`. Add `&sslnegotiation=direct` to save a round trip on
  servers that support it, such as Neon and Postgres 17.
- **Statement timeout:** each statement of a records request may run for at
  most 8 seconds, so an expensive filter cannot hold the database. A request
  over it fails with a 500. Change it with `statementTimeout` (milliseconds),
  or turn it off with `0`:

  ```ts
  export const nextbase = new NextBase({ statementTimeout: 3_000 });
  ```
- **Schema:** everything lives in the `nextbase` Postgres schema. The first
  request creates it, so the database role needs permission to create schemas
  and tables, or create the schema for it in advance.
- **Settings:** NextBase refuses to start unless `DateStyle` is `ISO` and
  `standard_conforming_strings` is `on`, the Postgres defaults.
- **Trigram indexes** install the `pg_trgm` extension, which needs the CREATE
  privilege on the database.

## File storage

Uploaded files are stored on local disk by default, in `.nextbase/storage`.
Serverless hosts such as Vercel keep no files between requests, so give
NextBase a bucket there: AWS S3, Cloudflare R2, MinIO or any S3-compatible
service. On Vercel, uploads without a bucket are refused rather than lost.
See [Files](/docs/guides/files#store-files-in-a-bucket).

## Migrations

NextBase upgrades its own tables on the first request after a deploy, under a
lock, so concurrent instances never run them twice. To do it before traffic
arrives, run it from a deploy script:

```ts title="scripts/migrate.ts"
import { nextbase } from "../lib/nextbase";

await nextbase.migrate();
```

When an upgrade adds a system field to auth collections, such as `phone`,
`phoneVerified` or `emailVerified`, a field of your own with that name is
renamed to `user_<name>` first, together with its column and the rules that
use it, and the server log says so. Its data is kept.

## Realtime

[Realtime](/docs/guides/realtime) listens for new events with Postgres
`LISTEN`, which transaction poolers do not support. With a pooled connection
string, such as Neon's `-pooler` host or Supabase's port 6543, set
`listenUrl` to the direct one. Each instance with open streams holds one
such connection, besides its pool.

```ts title="lib/nextbase.ts"
import { NextBase } from "@nextbasejs/core";

export const nextbase = new NextBase({
  realtime: {
    collections: ["messages"],
    listenUrl: process.env.DATABASE_URL_UNPOOLED,
  },
});
```

A realtime stream is a response that stays open. Serverless hosts cap how
long one may run: on Vercel, 300 seconds by default, and up to 800 on Pro.
NextBase ends each stream after `streamSeconds`, 240 by default, and the
client reconnects at once without missing events. Keep `streamSeconds` below
the route's `maxDuration`, for example to use longer streams:

```ts title="app/api/nextbase/[...path]/route.ts"
import { newNextHandler } from "@nextbasejs/next";
import { nextbase } from "@/lib/nextbase";

export const maxDuration = 800;
export const { GET, POST, PUT, PATCH, DELETE } = newNextHandler(nextbase);
```

with `streamSeconds: 780` in the `realtime` option. An open stream keeps its
function running, and on usage-billed hosts it is billed while open.

Each instance serves at most 1000 streams. Transactions that write to
realtime collections commit one at a time, which caps write throughput to
those collections at very high rates; see
[Limits](/docs/guides/realtime#limits).

## Logs

NextBase keeps a [log](/docs/guides/logs) of HTTP requests and background
failures in `nextbase._logs`, for 7 days by default. Each instance writes its
entries in the background, a burst at a time, and deletes expired ones about
every 10 minutes. On a busy app, keep `maxDays` short or raise `minLevel` to
`4` to keep only warnings and errors, so the table stays small. Outside
serverless hosts, call `await nextbase.flush()` before ending a pool you
passed in or before the process exits, so entries still waiting are not
lost.

To record client IPs with `logs: { ip: true }`, and to rate limit guests,
NextBase must know which header to trust. On Vercel it reads Vercel's own headers. Behind your own
proxy or load balancer, set `clientIp: { header: "x-forwarded-for" }`, with
`trustedHops` for each further proxy of yours. Without a header you control,
any client could claim any IP, so NextBase records none.

## Many instances

Serverless platforms run many copies of your app. A collection or rule change
made through one copy applies to every copy from its next request, and two
changes made at the same time never interfere. Realtime events reach the
streams of every copy: each write notifies all of them through Postgres.

## First superuser

On a fresh deployment, the server log prints a one-time setup token, valid for
one hour, until the first superuser exists. Only someone who can read your
logs can claim the deployment. Create the superuser right after the first
deploy, or ahead of time with `nextbase.createSuperuser(email, password)`.

## Security checklist

- Serve the app over HTTPS. In production the session cookie is
  `__Host-nextbase_session`, which browsers only accept as `Secure`.
- Check that guests are [rate limited](/docs/guides/rate-limits). NextBase
  limits every caller by default, but counts guests by IP, which it only
  knows on Vercel or with `clientIp` set to the header your proxy sets.
  Failed sign-ins are also limited per account (10 every 15 minutes).
- Review every collection's rules. New collections default to superuser-only.
- Keep superuser clients (`nextbase.client({ superuser: true })`) in trusted
  server code.
- Request bodies are limited to 1 MiB, or 32 MiB for form data carrying
  files.
